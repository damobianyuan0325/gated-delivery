# 持久化、SQL 与并发边界

只在改变或验收 SQL、数据库契约、缓存/快照或大报文路径时读取。生产操作仍须原授权、真实 Schema/索引与有界准入；示例优化不是普遍改写许可。

先确定项目实际使用的存储、驱动、事务边界与预算。下面MySQL的tuple/JSON/锁/执行计划文字仅适用于该引擎及相应操作，不要求其他项目改用MySQL；只读路径按其真实只读边界结束，不为套用写入例子制造commit或数据库写入。需要数据库真实契约证据的部分才做适配器集成验证；文档或无存储改动不自动承担整套数据库验收。

按本页适用条件选用检查，不把某一场景的流程升级为所有任务的默认步骤。

<a id="legacy-l062"></a>

枚举值或状态从代码跨入数据库时，逐项对照生产Schema的`CHECK`、枚举或字典约束；测试要穿过真实写入并由下游验收查询读回，不能只断言内存对象已经生成。使用`INSERT IGNORE`、忽略冲突的upsert或批量容错写入时，必须核对受影响行数和必需字段覆盖率，并加入一个约束不接受该状态时会失败的反例；外层事务成功、队列终结或HTTP 200不能证明每条证据已持久化。若业务允许新增状态，先迁移约束，再发布产生该状态的代码，并恢复此前因静默忽略形成的假终态。

<a id="legacy-l088"></a>

持久缓存或指标索引的失效清单须追踪共用SQL常量、写入helper的所有真实消费者，而不只看定义文件；沿实际写入事务验证事实与失效标记共同提交或回滚。依赖锁屏障建立快照或回填边界时，核对隔离级别、首次一致性读与锁定读的先后，以真实双连接覆盖旧写入跨屏障提交；锁定读不能修复已经建立的旧快照，也不能以倒置锁顺序补救。

<a id="legacy-l206"></a>

SQL集成验证使用目标驱动读回类型，特别是UNION、CAST和无符号数的推导，不能让只返回int的替身证明数据库契约。夹具若依赖产品构建器定义的时刻或格式，应经真实构建器生成合法输入，再对独立预期比较；手造非法结构导致的失败单列为夹具问题。

<a id="legacy-l208"></a>

当审计文档、规则摘要或进度凭据以JSON写入真实数据库并要求精确读回时，用高精度数值和真实量级报文覆盖数据库自身的数值/类型归一化；内存或简单整数夹具不能证明摘要稳定。保持严格校验，采用可逆编码或已验证的规范格式，不扩大容差来掩盖变化。同一数值格式还进入案例进度、自然结果等直接相关入口时，按同一失效条件验证其读回。

<a id="legacy-l210"></a>

更改数据库调度/筛选SQL时，在目标适配器验证无结果、最终批次为空及实际JSON标量比较；测试替身须匹配驱动的空行返回类型。内存空list、SQLite或简化JSON函数通过，不能证明MySQL空tuple、JSON布尔与SQL布尔的语义一致。至少一次真实refresh→commit→读取结果验收，保留普通任务公平份额。对查询结果新增排序、拼接或聚合时，空结果反例须经过这些新增处理和清理流程，不能只测驱动或上游适配器。

<a id="legacy-l212"></a>

涉及MySQL队列清理与领取事务时，以真实MySQL并发验证锁顺序、范围锁和隔离级别；SQLite串行或兼容适配器不能证明无死锁。遇1213先保留原并发反例，再按真实锁行为修复并用同一入口重验，不靠关闭并发或吞掉错误求绿。

<a id="legacy-l214"></a>

当页面数据由大JSON报告提供时，发布门禁必须实际读取数据API并验证用户内容，页面壳与健康端点HTTP200不够。大报文排序/筛选需按生产报文量级验证；仅缩小SELECT列不证明JSON不会进入排序，必须检查WHERE/ORDER所引用的字段并穿过真实读取路径。压缩后仍验证摘要、类型恢复、长度上限、旧格式兼容及各读取入口。

<a id="legacy-l216"></a>

临时取证查询同样检查大JSON的执行路径：即使只取长度或摘要，`ORDER BY`仍可能把原JSON带入filesort。遇到这类内存错误，优先验证先按原条件、顺序和LIMIT物化ID，再按主键读取的有界方案；用实际执行计划及原失败对象确认，没有依据不增大缓冲或超时。恢复只补未完成对象，保留已完成凭据和原失败记录。执行计划守卫按索引唯一性和实际基数界定允许范围，不把单一期望访问类型当稳定协议；例如主键单行被优化为`const`时不应仅因不是`eq_ref`而误拒，仍须验证主键与行数上界。

<a id="legacy-l218"></a>

发布本身会增加注册记录或改变数据分布时，发布前的执行计划不能替代发布后的成本验证；在隔离库或有界真实入口覆盖本次新增后的关键基数与筛选形状。原查询、显式等价访问的计划、参数和实际执行分别留证，固定索引路径须先核真实索引并保留原谓词、结果语义与负载守卫；不要只记录EXPLAIN而未执行准入，也不要因优化器改变就放宽预算。

<a id="legacy-l220"></a>

目标MySQL将已知缺失唯一键折叠为零行时，`EXPLAIN Extra`可能有不同的精确const空结果文字；先保存实际计划，再仅对同一精确查询、已验证唯一键条件和完整NULL计划形状接纳等价结果，保留其他查询、非NULL或大扫描拒绝反例，不泛放NULL计划或扩大预算。

<a id="legacy-l222"></a>

实际无表scalar SELECT的计划也可能含NULL行数与精确`Extra`文字。先保留完整raw plan，仅对已冻结的精确查询、typed args及录制的完整字段形状和节点集合做局部分类；不改raw，其他所有节点仍按原对象交原守卫。覆盖额外第三节点、物理字段非NULL及额外`Extra`反例；不全局lower/strip、不造rows=0、不放宽原预算，分类通过也不等于业务查询已执行。

<a id="legacy-l224"></a>

对现有数据库编写临时诊断SQL前，先从当前迁移/仓储查询确认字段，或在目标库执行`DESCRIBE`、`SHOW CREATE TABLE`、`information_schema`等只读结构查询；禁止凭记忆猜列名。同类`unknown column`诊断失败再次出现时，先回到结构证据并修正诊断模板，不继续试猜；临时查询失败不得冒充产品或服务故障。

<a id="legacy-l226"></a>

Schema预检按本轮查询首次引用的每一张真实表逐表生效；已经检查同批其他表、曾在更早轮次看过该表，或某个前序语句成功，都不能覆盖新表的结构证据。多语句诊断提交前列出全部真实表并逐一绑定字段来源；若无法证明某字段来自真实表列，先把查询拆开并执行结构检查。

<a id="legacy-l228"></a>

复制Dashboard、报表或子查询中的名称到生产诊断时，必须区分真实表列与SELECT/CTE派生别名；派生别名只能在其合法作用域使用，跨查询统计要复制被验证的原表达式或显式建立CTE。相互独立的诊断证据不要塞进一条会因前序错误整体中止的多语句命令；先完成Schema预检，再分组执行并逐项确认输出完整。
