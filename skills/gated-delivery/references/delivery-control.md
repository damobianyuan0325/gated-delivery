# 交付控制与有限收尾

只在多包、依赖、轮次或续做确实需要账本时读取。轻量任务无需因此另建账本；按本轮适用对象执行，不扩大需求、权限或自然观察期限。功能包的验收与收尾规则见下文。

按本页适用条件选用检查，不把某一场景的流程升级为所有任务的默认步骤。

<a id="legacy-l012"></a>

目标：按需求逐项实现，用可复核证据证明结果，失败修复后重测，通过后直接继续依赖已满足的下一项。不要用反复汇报小进展代替完成整个授权范围。

<a id="legacy-l016"></a>

先读项目规则、用户指定需求、现有计划及实际源码。已存在的账本继续使用，避免另建一份相互矛盾的计划。

<a id="legacy-l018"></a>

没有账本时先用简短任务记录列出整体目标、核心链路、关键风险和下一步；仅当复杂依赖或交接确实需要时，选用 [assets/gate-plan.md](../assets/gate-plan.md) 中必要部分。路径服从项目约定。需求变更记录差异，不整篇复制旧历史。

<a id="legacy-l020"></a>

- 复杂依赖或重要风险需要追踪时，用稳定 ID 关联需求、验收、检查与证据；一般任务使用现有清单即可。
- 先写清主流程的输入、可观察结果及关键约束，再随重要模块推进补充必要边界和异常，不在动手前穷举所有细节。
- 模糊需求不得编造成已确认事实。低风险、可逆的细节可列出假设后推进；会改变业务逻辑、资金风险、数据契约或权限的关键歧义，提出最小必要问题。其余不依赖该决定的工作继续。
- 区分范围内必做、用户暂缓、可选。暂缓不等于通过；若必做项依赖暂缓项，明确说明影响，不能绕过。
- 不把某个项目的数据库、交易平台或生产配置写成所有项目必须使用的规则。

<a id="legacy-l028"></a>

以用户可使用的功能包组织工作，不把每个字段、文案、测试或修复都拆成新的长期目标。开始前为每包记录：具体交付物、必做行为、关键异常、验收层级、有限的验收清单、非目标、修复轮次和完成后的下一包。范围清楚时直接制定并执行，不反复询问已授权步骤。既有测试与运行证据有效则复用，不为凑轮次重测。

<a id="legacy-l030"></a>

默认先做一轮功能验收，再集中修复重验，必要时第三轮收尾；用户指定的轮次、时间或范围优先。一轮指围绕同一功能清单的检查→修复→受影响回归，不是一次工具调用、测试用例或发布。达到清单要求且没有影响使用的明确缺陷，即冻结该包并推进下一包，不为了假想风险、代码更漂亮或新发现的可选优化反复改版。

<a id="legacy-l032"></a>

发现问题先分类：阻断必做功能或造成错误结果的是当前必修项；不影响约定功能的美化、重构、极端未要求场景进入可选清单，不自动开发或发布。已结项功能仅因真实回归、明确安全/资金/数据错误或用户新增需求重开，并列具体失败证据与受影响标准；不得用泛泛的“更严谨”重开全部审计。下文的专项检查只在修改或验收确实涉及对应风险时应用，不逐条强加到每个功能。

<a id="legacy-l034"></a>

达到约定轮次仍未过，交付具体未完成项、影响与另一种有限解决方案；继续可独立完成的功能。不得自行把同一单元延展成无期限修复，也不得通过拆新单元清零轮次。需改变已约定范围或增加一轮工作时明确说明变化依据，按用户指示调整。明显安全、账本、错误外发等缺陷不能因轮次用尽而上线或标通过。

<a id="legacy-l036"></a>

区分功能开发完成、真实运行验收、持续业务效果。缺少自然样本或用户关闭外部功能时，明确未验收部分；不能造样本冒充生产，也不能把等待未来收益/事件变成无限开发工期。一个功能包通过不代表整个目标完成；总体收尾必须对照全部必做功能报告完成、未完成及原因。状态更新优先报告功能结果及剩余项，不以修复次数、版本次数或测试数量代替功能进度。

<a id="legacy-l112"></a>

围绕整体用户流程组织实现，先接通最小端到端路径；按价值、风险和依赖逐步完善模块。仅在确有并行或交接需要时拆成独立单元并记录必要依赖。

<a id="legacy-l114"></a>

组件开发、应用接线、用户入口、持久化、错误恢复、部署分别标记；仅组件完成不得把整个功能标为完成。尽早实现最小端到端路径，避免积累大量不能从实际入口调用的“已完成组件”。

<a id="legacy-l118"></a>

单元状态：`TODO → READY → IN_PROGRESS → VERIFYING → PASSED`。

<a id="legacy-l120"></a>

- 失败回到 `IN_PROGRESS`，保留失败记录和原因。
- `BLOCKED` 必须说明缺失信息/环境/权限、影响范围及解除条件。
- `DEFERRED` 必须有用户依据，不得计入通过数量。
- 按实际依赖推进：缺少运行事实时不能声称运行通过；实现契约明确时可先开发并隔离测试。可推进真正独立的单元，记录改序原因。

<a id="legacy-l125"></a>

遇到阻断时区分“实现依赖”和“上线依赖”：外部验收未完成，不必阻止可独立测试的代码、只读诊断和部署准备；但不能据此放行生产。不要为了展示进度反复添加已有行为的同义测试。恢复执行先读取上次证据，只有新输入或状态变化才重复同一外部检查。

<a id="legacy-l131"></a>

在当前授权范围内先贯通核心路径，再按重要程度推进剩余必做功能，直到完成或不存在可安全推进的工作。以下步骤只在单元化管理确有帮助时使用：

<a id="legacy-l133"></a>

1. 读取下一个 READY 单元及其用例，确认依赖和环境。
2. 增补测试、实现最小完整功能，保留用户已有修改。
3. 运行该单元测试与受影响模块回归；不能只检查语法或编译。
4. 失败时依据日志定位、修复并重测。默认修实现，不靠删除断言、扩大容差、跳过测试或弱化业务约束来求绿；测试本身错误时说明依据并修正。
5. 通过后核对需求覆盖、真实入口接线和必要人工验证，记录 E 与代码版本，再标记 PASSED。
6. 简短报告有意义的进度，然后直接开始下一个 READY 单元，不用最终答复结束回合来等待“继续”。

<a id="legacy-l152"></a>

保持必要的进度沟通，但不把每条测试输出都发送给用户。未完成时不得因“已有很多测试通过”就宣布整个任务完成。

<a id="legacy-l276"></a>

连续开发的授权不等于生产操作授权。默认使用隔离环境和假数据，不读取或打印不必要的密钥，不复制生产数据库进入测试。

<a id="legacy-l278"></a>

真实下单、划转、取消用户订单、破坏性迁移、对外通知、公开发布、影响活跃生产服务的部署/重启等操作，必须在用户授权范围内，遵守项目门禁和工具权限。不能为了做端到端测试擅自执行。缺少授权时继续可独立完成的源码/测试工作，最后说明所需决策。

<a id="legacy-l280"></a>

技能是当前会话的执行规程，不是独立后台进程；不承诺关掉会话后会继续开发。用户需要后台持续执行时先确认可用执行机制与权限，不能自行安装定时任务来反复唤醒模型。

<a id="legacy-l284"></a>

- 优先运行最小相关测试集；集成节点和最终交付运行适当的完整回归。测试未变、代码未变时不反复运行同一全量套件。
- 高频Supervisor/定时组件的运行历史应在状态变化时立即持久化，状态不变时按心跳窗口合并；既要保留重启后的最后成功/失败证据，也要测试空转任务不会按秒制造无界写入。
- 将高频机械检查交给现有测试框架、脚本或 CI，不让模型手工重复判断；不擅自引入新框架或付费服务。
- 日志保存到文件，只读取失败片段和摘要；不在计划中粘贴整份日志、密钥或长源码。
- 上下文不足或被中断前，在账本记录当前单元、改动、最近失败、证据、下一条具体动作；恢复时先读账本并核对实际代码，不从头重做、不重新请求已有授权。

<a id="legacy-l292"></a>

用户要求持续完善技能时，只将本轮已观察到的执行缺陷提炼为小幅通用修正，记录依据并验证；项目专属状态留在项目账本。获得持续维护授权后，主动维护本技能及本轮实际使用、确有同类缺陷的相关技能，不再重复询问；无新证据不改版，不将单项案例扩成无关技能的普遍限制。技能维护不得替代主任务或新增无限扩展的开发范围。区分仓库技能副本与已安装副本，未同步时明确说明。

<a id="legacy-l294"></a>

按本页功能包规则完成收尾。整体目标只有全部必做功能达到约定验收层级才可标完成；用户暂停/更改任务时遵从，真正依赖缺失输入或环境的部分明确列出，并继续独立可做工作。轮次用尽不是通过证据，也不能据此把整体目标标完成。

<a id="legacy-l296"></a>

交付前检查每条需求映射、最终回归、非目标保护、已知问题与部署状态。最终答复简洁写明完成了什么、实际测试结果、未完成/阻断项及必要下一步；不得把暂缓或未验收项包装成完成。若无法完成，明确说明而不是承诺后台自动继续。
