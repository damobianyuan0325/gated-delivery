# 验证驱动交付

2.3.2。方法见[设计原则](references/design-principles.md)；版本说明见[变更记录](CHANGELOG.md)，按需读取。仓库候选、已安装和实际运行版本分别记录，不冒称已发布。

先理解用户目标并直接推进可交付结果。重要业务选择由任务责任人决定；自动检查提供可复核的事实，不能代替对业务结果的判断。

这是跨项目的研发主技能。工作约定采用通用工程表述；具体业务只是应用场景。链名、评分/交易门槛、数据库预算、特定服务和运行状态留在项目自己的约定与配置中，不提升为其他项目的默认限制。

## 先选足够的执行方式

- **小而可逆**：目标和影响面清楚时直接修改，做相关差分、链接或最小行为检查，简述结果。无需新建长期目标、完整 JSON 账本或为每处文案写测试。
- **多单元、难恢复或高风险**：复用项目唯一账本；没有时按 [gate-plan.md](assets/gate-plan.md) 记录有限范围。只读取实际相关细则。关键业务、资金、数据契约或权限歧义才问最小必要问题；独立工作继续。

## 建立最小可用 Harness

开始研发时先复用项目的 `AGENTS.md`、现有测试/CI与工具，确认任务入口、可用工具、主要风险和检查方式。首次接手、环境不明或长任务续做时读 [Harness 工作约定](references/harness.md)；需要留项目说明时用 [简版模板](assets/project-harness.md)，已有约定不重复造文件。小任务只核相关源码、一个有效检查入口和权限即可。

先证明所选解释器、依赖/夹具、检查命令与实际源码归属可用，再执行依赖它们的步骤。前置检查失败就停止相应修改/发布，不把报告器报错当成检查成功后继续；修正前置条件后只重验受影响项。复用已验证工具，不为每个缺陷重新搭发布、验收或备份框架。

## 在实现前固定验收

对多模块或需求不清的任务，在编码前投入足够精力拆解需求：从用户入口到最终结果梳理完整主流程、各环节输入输出、依赖、现状与缺口、关键异常及验收方式，标明必做和后续项；复用已有记录，详见[需求澄清与复用](references/requirements-and-reuse.md)。关键歧义提出具体选项并说明影响；能从代码核实的先核实。低风险可逆的小任务保持轻量，拆解不以文档长度或固定时长衡量。

验收先写主流程的可观察结果和不可违反的边界。已有账本直接复用；只有复杂依赖或重要风险需要追踪时才细分标准和关联证据，不为普通功能逐项建立 R/A/T/U/E 矩阵。检查预期须独立于实现，缺失、未知与数值零分开。

默认先贯通从用户入口到主要结果的最小完整流程，接好必要模块、数据与展示，用一次真实入口检查确认链路可用；如存在多个必需入口，先覆盖最核心的路径并明确其余缺口。随后按用户价值、风险和依赖排序补齐重要模块、异常与回归，低优先级细节后置。首条路径通过是阶段进展，不代表全部需求完成；资金、权限、数据安全等不可违反的边界在首次贯通时就要保护。

开发中新发现先判断：阻断已约定主流程或触及明确安全、权限、资金、数据边界的本轮处理；不阻断的优化、新能力和假设风险记录后续，不自行扩张任务。若关键依赖或验收目标改变，说明影响并与用户对齐；持续报告真实可用路径、未完成项和下一步，而非检查数量。

## 连续实现、判断、修复

在授权内推进 READY 单元，不以进度答复等用户说“继续”。先复用有效测试和证据，再增加能区分正确/错误的检查。缺陷尽量先重现；新行为可先跑暴露缺失的用例。已有测试不必全部变 RED；不能伪造先失败，或为低影响修改堆测试。

处理多个问题时，先确定当前问题的范围和验收，再完成修复、针对性测试及约定的真实入口验收；已有部署授权且本次需要上线时，单独上线并核实实际结果，再处理下一个。未授权部署不自行上线；部署或验收受阻时记录原因、影响和未完成状态，不假称通过，可继续不依赖该阻断的工作。非阻塞新问题记录到现有待办，不顺势扩大当前改动；小而可逆的工作按风险简化。

默认按独立需求修实现。测试前提确实错误时，保留首失败，引用真实契约后只修错误前提；不得删断言、扩大容差、跳过必要检查或改业务门槛求绿。受阻记 BLOCKED/NOT_RUN，保留本地已证范围；CI 受阻不等于通过，不自动绕过 required checks、分支保护或权限。

固定失败对象、预算和同条件矩阵后集中修复、重测受影响项。新输入或真实状态变化才重试；无新证据不反复探测。实现依赖与上线依赖分开，继续真正独立的单元。达到停止条件仍失败时交付缺项和有限替代方案，不能拆单元清零预算或无限审计。

## 机器核验的范围

需要可重复的执行凭据时，使用 [JSON 示例](assets/delivery-plan.example.json)、[run_check.py](scripts/run_check.py) 和 [check_delivery.py](scripts/check_delivery.py)，接口以帮助和示例为准。命令是计划数据，不是额外授权；只执行调用方明确给出的已授权命令。人工账本保留 R/A/T/U/E，JSON 只表达工具支持字段。

核验器检查最终源码 SHA、命令一致、返回码、计数/跳过、输出 hash 及 A/T 覆盖层级等确定性凭据；它不证明预期独立、断言充分、业务正确、真实生产环境或 CI 分支保护已满足。机器通过后仍按约定入口复核业务证据。

## 冻结与收尾

必做 A 全部在要求层级有有效 E 才通过；实现、验证、运行观察及部署分别报告。已验包立即冻结摘要并推进下一包；重开要有真实回归、明确错误或用户新要求。最终对照全部必做范围交付完成、未验/阻断项、实际证据及必要下一步，不用测试数量、自然结果等待或外部宣传数据冒充效果。

真实漏检先找缺失输入、调用边界或断言，优先把守护留在项目；只有跨项目成立的教训才回流本技能。比较效果时用已有记录中的交付耗时、人工介入、返工及真实用量，不另造长期审计或凭入口字数推算 token 节省。关于实际效果与保护措施的说法须有对应证据；本地工具通过不等于远端合并保护已启用，也不据此宣称成熟度认证或零缺陷保证。
